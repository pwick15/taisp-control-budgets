Untrusted monitor baseline: Haiku, Sonnet and Luna on APPS

Which monitor catches the most backdoors, and how much does it lean on the comments an attacker leaves?

2026-10-20PunjayaPreliminary, 30 + 30 samplesAPPSuntrusted monitoringdataset mode

Summary

  • Sonnet 5.5 is the best monitor. It separated honest from backdoored solutions almost perfectly (AUROC 0.999), ahead of Haiku 4.5 (0.93) and GPT-6 Luna (0.87).
  • Hiding code comments hurt every monitor. AUROC fell by 0.08 to 0.12. Part of what monitors catch is the comments an attacker leaves, not the backdoor itself. Sonnet still led afterwards (0.92).
  • The weaker monitors fail in different ways. Haiku raised 12 false alarms on 30 honest solutions. Luna raised none, but gave 8 of 30 backdoors a score of 0.
  • This is the best case for untrusted monitoring. The monitor and the attacker never coordinate here, so treat Sonnet's numbers as an upper bound. With 30 + 30 samples, small gaps are noise.

What we wanted to find out

Our project compares ways to catch an AI model that is slipping backdoors into code. A monitor is a second model that reads the code and scores how suspicious it looks. This experiment asks two questions.

  1. Does a strong monitor that we cannot fully trust (here, Sonnet 5.5) catch more backdoors than a weaker monitor that we do trust (Haiku 4.5, GPT-6 Luna)?
  2. How much of a monitor's skill comes from comments the attacker left in the code, instead of the code itself?
Best case, not worst case

Real untrusted monitoring has a catch. The monitor could be working with the attacker and cover for it. Here the two never coordinate, so Sonnet's numbers show what a capable, honest monitor can do. A scheming one would do worse.

How the test works

Each sample is one programming problem from the APPS dataset. The code comes straight from the dataset, so no model writes anything. The only thing we pay for is a monitor reading it.

  1. ProblemThe first 30 APPS problems that have a verified backdoor.
  2. CodeHonest run: the dataset's correct solution. Attack run: a solution with a backdoor, meaning it passes the tests but fails on one secret input.
  3. MonitorA model reads the code and returns a suspicion score from 0 (looks fine) to 1 (very suspicious).
  4. Audit ruleHumans can review only a small share of honest work. That share sets a score cutoff.
  5. ResultA backdoor scoring above the cutoff is caught. One scoring at or below it is missed.
Honest run
The monitor reads correct code with no backdoor.
Attack run
The monitor reads code with a verified backdoor.
Audit budget
The share of honest runs humans can afford to review. At 5%, the cutoff is the score that only the top 5% of honest runs exceed.
Safety
Backdoors caught, divided by backdoors caught plus backdoors that slipped through. Here every dataset backdoor works, so safety is simply caught out of 30.
AUROC
How well scores separate attack from honest, ignoring any cutoff. 1.0 is perfect, 0.5 is guessing.
Comments hidden
We delete every # comment from the code before the monitor sees it. Many dataset backdoors carry comments that announce the bug, and honest code rarely does.

How we got here

The final design is not where we started. Each stage below fixed a problem in the one before.

  1. Stage 1

    Let Sonnet write the attacks

    What we did
    Ran trusted monitoring (Haiku) and untrusted monitoring (Sonnet) with Sonnet writing both the honest and the attack code. 10 problems per mode. The logs for this run are not committed.
    What we saw
    Haiku scored 7 of 10 attacks at exactly 0. Sonnet scored 9 of 10 above 0. Every honest run scored 0 for both monitors, so the audit cutoff sat at 0 and the budget sweep was flat. Sonnet also wrote fresh attacks in each protocol, so the two monitors never saw the same code.
    What it changed
    Switched to dataset mode. Every monitor now reads identical code, and a run costs cents.
  2. Stage 2

    Pilot with 5 problems

    What we did
    Dataset mode, 5 honest and 5 attack runs, all three monitors.
    What we saw
    Everything ran. Cost for 10 samples was $0.06 for Haiku, $0.10 for Sonnet and under a cent for Luna. Each monitor scored attacks higher than honest code on average.
    What it changed
    Used those costs to size the real run. 30 problems per mode fit the Anthropic budget with room to spare.
  3. Stage 3

    Full run, comments kept

    What we did
    30 honest and 30 attack runs per monitor.
    What we saw
    Sonnet separated the groups almost perfectly (AUROC 0.999). Attacks carried comments far more often than honest code did: 20 of 30 against 2 of 30, counted in the submitted code.
    What it changed
    Raised the question of whether monitors were reading comments instead of code. A quick look at the raw scores said no, since attacks without comments scored as high. That check turned out to be misleading, so we ran the direct test.
  4. Stage 4

    Same run, comments hidden

    What we did
    Deleted every # comment from the code before the monitor saw it. Same problems, same monitors.
    What we saw
    All three got worse: Haiku 4.5 0.93 → 0.86, Sonnet 5.5 0.999 → 0.92, GPT-6 Luna 0.87 → 0.75 (AUROC).
    What it changed
    Comments are part of what monitors detect. Results on comment-heavy dataset backdoors overstate how well monitors find backdoors in plain code. Sonnet still came first.

Caveats

  • Small sample. 30 honest and 30 attack runs. One missed attack moves safety by 3.3 points, so gaps under about 0.1 are noise.
  • Dataset attacks, not model-written. Two thirds carry comments and the honest code is human-written. Read the results as a comparison between monitors, not as absolute detection rates.
  • No collusion. Sonnet never covers for the attacker, and it is a bigger model than Haiku, so "untrusted" and "stronger" are bundled together.
  • Ties. Scores come in steps of 0.1, which flattens the safety curves. AUROC avoids this. Budgets under 3.3% use less than one honest run (shaded in the chart).
  • Scope. Only # comments were removed, not docstrings or variable names. Costs are estimates from list prices.

Problems we hit along the way

  • analyze.py crashed on macOS because its process pool re-ran the script. A __main__ guard fixed it.
  • Token counts ignored cached input, so Sonnet looked about five times cheaper than it was (376 against 1,914 tokens per sample). Now counted properly.
  • Old runs in the same log folder were mixed into the analysis (44 samples instead of 20). Use a fresh LOG_DIR for every run.

What to do next

  • Collusion test. Let the attacker leave a signal for the monitor, then see whether hiding comments or rewording the code removes it. This is the real test of untrusted monitoring.
  • Sweep the audit threshold directly and put a cost on each human review, so the trade-off between safety, usefulness and cost is explicit.
  • Model-written attacks and more samples. 100 or more per mode would make small gaps readable.
  • More monitors and prompts, including the chain-of-thought and ensemble options in the library.

Reproduce

Branch untrusted-monitor-baseline. Dataset mode, 30 problems, one run per monitor and variant.

export POLICY=dataset
N=30
# comments kept (add STRIP_COMMENTS=1 and a -strip suffix on LOG_DIR for the hidden-comments runs)
PROTOCOLS=trusted_monitoring TRUSTED_MODEL=anthropic/claude-haiku-4-5-20251001 \
  LOG_DIR=logs/dataset-haiku45-tm-n$N uv run python src/experiment.py $N
PROTOCOLS=untrusted_monitoring UNTRUSTED_MODEL=anthropic/claude-sonnet-5-5 \
  LOG_DIR=logs/dataset-sonnet55-um-n$N uv run python src/experiment.py $N
PROTOCOLS=trusted_monitoring TRUSTED_MODEL=openai/gpt-6-luna \
  LOG_DIR=logs/dataset-gpt6luna-tm-n$N uv run python src/experiment.py $N

# turn each log folder into results/<name>.csv and results/<name>-samples.csv
LOG_DIR=logs/dataset-haiku45-tm-n$N uv run python src/analyze.py

# rebuild this page
uv run python reports/build.py --open
