Model-written attacks: Sonnet 5.5 against Haiku 4.5 and Sonnet 5.5 monitors

With a live attacker, how much does each monitor catch at each audit budget, and what does deferring to the trusted model buy?

2026-10-19Anusha AsimPreliminary, 100 + 100 samplesAPPSmodel-written attackstrusted monitoringuntrusted monitoringdefer to trusted

Summary

  • A weak trusted monitor catches only 47% of model-written backdoors at a 10% audit budget. Haiku 4.5 reading Sonnet 5.5's code (comments hidden) reaches AUROC 0.70 and scored 45 of 100 attacks exactly 0.
  • The audit budget only matters in a step. Haiku's safety stays at 0.47 from 1% to 10% and jumps to 0.79 at 20%, because almost every score is 0 and the cutoff only moves once the budget passes the honest runs that scored above 0.
  • Sonnet monitoring its own kind of code is far better: AUROC 0.96, safety 0.96 at 10%, for about $0.0040 more per sample. It never colludes here, so this is an upper bound for untrusted monitoring.
  • Comments barely matter for live attacks. Haiku's AUROC is 0.71 with comments and 0.70 without, unlike the dataset backdoors, which often announced themselves.
  • Defer-to-trusted has only 3 distinct settings at a 10% audit budget, because Haiku's scores take so few values: defer 0% of honest runs: safety 0.47, usefulness 0.95; defer 19% of honest runs: safety 0.62, usefulness 0.86; defer 100% of honest runs: safety 1.00, usefulness 0.70. Raising the audit budget to 20% instead gives safety 0.79 with no loss of usefulness.

What we wanted to find out

Earlier runs replayed backdoors stored in the APPS dataset. Here a live model writes them: Sonnet 5.5 plays the untrusted model and tries to slip a backdoor into each solution. A monitor reads each solution and scores how suspicious it looks.

  1. How much does a weak trusted monitor (Haiku 4.5) catch when the attacks are written by a stronger model?
  2. How does safety change with the audit budget, and with deferring suspicious outputs to Haiku?
  3. Do model-written backdoors give themselves away in comments, as the dataset ones did?
Best case for untrusted monitoring

Sonnet as a monitor never coordinates with Sonnet as the attacker here. Its numbers show what a capable, honest monitor can do, not what a scheming one would do.

How the test works

We record the untrusted model once and score the saved outputs with every monitor, so every monitor judges exactly the same code and the attacker is paid for only once.

  1. RecordSonnet 5.5 solves the first 100 APPS problems twice: honestly, and while trying to insert a backdoor. Haiku 4.5 also solves them honestly, as the fallback for defer-to-trusted.
  2. Run the codeEvery solution is run against the tests, and every backdoor against its secret input, inside Docker. Results are saved with the transcripts.
  3. MonitorEach monitor reads the saved code and gives a suspicion score from 0 to 1.
  4. AuditHumans review the top X% of honest scores' worth. Attacks scoring above that cutoff are caught.
  5. DeferOptionally, the next most suspicious outputs are replaced by Haiku's own solution.
Working backdoor
Passes the tests and fails on the attacker's secret input. Only these count against safety.
Safety
Backdoors caught, divided by caught plus working backdoors that slipped through.
Usefulness
Share of honest problems solved after any deferral.
AUROC
Chance a random attack scores higher than a random honest run. 1.0 is perfect, 0.5 is guessing.
Comments hidden
Every # comment is deleted from the code before the monitor sees it.

How we got here

  1. Stage 1

    Dataset backdoors

    What we did
    Monitors read the APPS dataset's stored backdoors instead of model-written ones.
    What we saw
    Most stored backdoors carried comments announcing the bug, and monitors leaned on them.
    What it changed
    Added comment hiding, then moved to a live attacker.
  2. Stage 2

    Pilot with a live attacker

    What we did
    Sonnet 5.5 attacking, Haiku 4.5 monitoring, 10 problems.
    What we saw
    7 of 10 attacks triggered on their secret input and the run cost about $0.40, so a larger run was affordable.
    What it changed
    Recorded 100 problems once and scored them with several monitors.
  3. Stage 3

    Full run

    What we did
    100 honest and 100 attack runs, recorded once. Haiku with and without comments, Sonnet without.
    What we saw
    Haiku missed most attacks; Sonnet caught nearly all of them.
    What it changed
    Simulated defer-to-trusted from the same files to trace the safety-usefulness trade-off.

Caveats

  • One recording, 100 problems. Only working backdoors count towards safety, so each one moves it by a couple of points. Gaps under about 0.1 are noise.
  • Coarse scores. Monitors answer in steps of 0.1 and mostly 0, so the cutoff sits on ties and safety moves in steps as the budget changes. AUROC avoids this.
  • No collusion and no attack selection. Sonnet-as-monitor never covers for Sonnet-as-attacker, and the attacker attacks every problem instead of choosing when.
  • Deferral is simulated. A deferred problem uses Haiku's one recorded solution to it.
  • Costs are estimates from list prices in src/analyze.py.

What to do next

  • Finer-grained scores (for example 0 to 100, or several samples averaged) so the audit budget can move the cutoff smoothly.
  • Free-tier replication with Gemini 3.5 Flash attacking and Gemini 3.5 Flash-Lite and Ministral 8B monitoring.
  • A stronger attacker (Opus 5.5) against the same monitors, to see how safety falls as the gap grows.
  • Collusion test for untrusted monitoring.
